Pertemuan 8

Middleware pada Sistem Terdistribusi

Jembatan penghubung antar komponen sistem

P8 · A

Capaian Pembelajaran

Setelah pertemuan ini, mahasiswa mampu:

  • Menjelaskan pengertian middleware dalam sistem terdistribusi
  • Menjelaskan fungsi middleware sebagai penghubung antar komponen
  • Mengidentifikasi jenis-jenis middleware
  • Menjelaskan konsep message broker, API gateway, dan service discovery
  • Menganalisis peran middleware pada aplikasi modern (e-commerce, mobile banking, cloud, ride-hailing)
P8 · B

Apa itu Middleware?

Middleware adalah perangkat lunak yang berada di antara aplikasi, sistem operasi, jaringan, database, atau layanan lain untuk membantu komunikasi dan integrasi antar komponen.

Client
→
Middleware
→
Service A
Service B
Service C

Middleware sebagai jembatan penghubung antara client dan backend service.

P8 · C

Mengapa Middleware Dibutuhkan?

❌ Tanpa Middleware

Service A harus tahu detail Service B, C, dan D. Komunikasi rumit, sulit di-maintain, sulit scaling.

✅ Dengan Middleware

Service A cukup bicara dengan lapisan perantara. Middleware mengurus routing, format, security, retry.

Manfaat utama:

Cross-platform Data transformation Komunikasi sederhana Keamanan Skalabilitas Monitoring & logging
P8 · D

Fungsi Middleware

📡

Communication Management

Mengatur komunikasi antar komponen (client → API Gateway → service).

🔄

Data Transformation

Konversi format: XML ↔ JSON, JSON ↔ object, object ↔ message.

🔗

Service Integration

Menggabungkan User, Product, Order, Payment, Shipping menjadi sistem utuh.

⚖️

Load Balancing

Membagi beban request ke beberapa server agar tidak overload.

🔐

Security Handling

Cek token login, hak akses, validasi request, enkripsi komunikasi.

🛡️

Error Handling

Retry, fallback, redirect ke server lain, log kegagalan.

Message Broker

Perantara pengiriman pesan antar service secara asynchronous — pengirim tidak perlu menunggu penerima selesai memproses.

Producer
Order Service
→
Message Broker
RabbitMQ / Kafka
→

Shipping Service
Notification Service

Synchronous

Asynchronous

Client kirim pesan → lanjut kerja. Consumer proses di background.

P8 · H

Service Discovery

Mekanisme agar service dapat menemukan alamat service lain secara otomatis. Penting karena alamat bisa berubah (autoscaling, restart, deploy baru).

1
Service A mendaftar ke Service Registry
2
Service B mencari alamat Service A di Registry
3
Service B mengirim request ke Service A (alamat terbaru)
Service Provider Service Consumer Service Registry

Contoh: Consul, Eureka, etcd, Kubernetes DNS

P8 · Kesimpulan

Kesimpulan Middleware

"Middleware membuat sistem yang kompleks terlihat lebih sederhana dan terstruktur bagi pengguna maupun pengembang."

  • Middleware = penghubung antar komponen sistem terdistribusi
  • Membuat sistem lebih terorganisir, mudah di-maintain, dan scalable
  • 3 middleware utama: Message Broker, API Gateway, Service Discovery
  • Digunakan di hampir semua aplikasi modern (e-commerce, banking, ride-hailing)
Pertemuan 9

Fault Tolerance & Reliability

Membangun sistem yang tetap berjalan saat ada kegagalan

P8 · A

Capaian Pembelajaran

Setelah pertemuan ini, mahasiswa mampu:

  • Menjelaskan konsep fault, error, dan failure
  • Mengidentifikasi jenis kegagalan dalam sistem terdistribusi

  • Memahami teknik: redundancy, replication, checkpointing, failover, retry, timeout, recovery
  • Menganalisis strategi peningkatan reliability pada sistem nyata
P8 · D

Fault → Error → Failure

Fault tolerance = kemampuan sistem tetap memberikan layanan meskipun sebagian komponen gagal.

Fault

Penyebab masalah
Bug pada kode pembayaran

→

Error

Kondisi tidak benar
Data transaksi salah

→

Failure

Layanan gagal
Pembayaran gagal

"Sistem yang baik bukan yang tidak pernah gagal, tetapi yang tetap berjalan saat ada kegagalan."

P8 · E

P8 · F

Reliability vs Availability

🎯

Reliability

Kemampuan sistem memberikan layanan yang benar dalam jangka waktu tertentu.

Fokus: kebenaran output

⏰

Availability

Kemampuan sistem untuk tersedia saat dibutuhkan.

Fokus: uptime

Sistem bisa available tapi tidak reliable — tersedia tapi hasilnya salah.

P8 · G

Teknik Fault Tolerance

🔁 Redundancy

Komponen cadangan agar sistem tetap jalan jika komponen utama gagal.

📋 Replication

Salin data/service ke beberapa node. Tingkatkan availability.

🔀 Failover

Perpindahan otomatis ke komponen cadangan saat utama gagal.

💾 Checkpointing

Simpan kondisi sistem di titik tertentu. Gagal? Lanjut dari checkpoint.

🔄 Retry & Timeout

Coba ulang request gagal (dengan batas). Timeout = batas waktu tunggu.

🔌 Circuit Breaker

Hentikan request ke service bermasalah. Cegah kerusakan menyebar.

P8 · G.3

Failover & Circuit Breaker

Failover

✓
Normal: Client → Server Utama → DB
⚠️
Server utama gagal
✓
Auto: Client → Server Cadangan → DB

Circuit Breaker

🟢
Closed — request normal
🟡
Half-Open — coba kirim sedikit
🔴
Open — stop request, return fallback
P9 · H

Studi Kasus: Mobile Banking

Mobile banking harus sangat reliable — berhubungan dengan uang dan transaksi.

⚠️ Risiko

  • Transaksi gagal
  • Saldo tidak update
  • Pembayaran ganda
  • Server overload
  • Response lambat

✅ Strategi FT

  • Redundancy server
  • Database replication
  • Idempotent retry
  • Circuit breaker
  • Graceful degradation

P9 · J

Fault Tolerance dalam Microservices

Satu service gagal tidak boleh membuat seluruh sistem mati.

🎭 Graceful Degradation

Sistem tetap jalan meski sebagian fitur tidak tersedia. Contoh: Recommendation mati, tapi checkout tetap bisa.

🔄 Fallback

Layanan alternatif ketika service utama gagal.

🧱 Bulkhead

Batasi dampak kegagalan agar tidak merambat ke seluruh sistem.

📊 Monitoring & Alerting

Deteksi gangguan cepat, notifikasi tim saat anomali.

P9 · Kesimpulan

Kesimpulan Fault Tolerance

"Dalam sistem terdistribusi, kegagalan bukan pengecualian. Kegagalan adalah sesuatu yang harus diasumsikan sejak awal desain."

  • Fault tolerance = sistem tetap berjalan saat ada komponen gagal
  • Teknik utama: redundancy, replication, failover, retry, circuit breaker
  • Reliability ≠ Availability — keduanya penting
  • Graceful degradation lebih baik daripada total failure
  • Desain untuk kegagalan sejak awal (Design for Failure)
